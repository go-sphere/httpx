# httpx benchmarks

**Current baseline: [BENCHMARK.md](BENCHMARK.md)** — all five adapters (ginx, echox, fiberx,
hertzx, stdx) against the framework each one wraps (gin, echo, fiber, hertz, net/http),
generated by `make bench-report`.

```sh
make bench-report                 # 12 samples x 200ms, network and gin appendix included
make bench-report BENCH_COUNT=4   # a quick look
python3 benchmarks/report.py --skip-network --skip-gin-depth
python3 benchmarks/report.py --help
```

## Why there is a driver script

The four targets below each measure one table. They are for iterating — change an
implementation, see whether that one table moved — and **two of their runs are two different
environments**: a different compiled binary, a different machine state, possibly a different
commit. Every report was once produced that way and written up by hand, which is why nothing
in `history/` can be quoted next to anything else.

`report.py` exists to fix exactly that:

1. it compiles the conformance tests into **one binary**, and measures all three in-process
   tables from that same binary — one compilation, one set of inlining decisions, one set of
   dependency versions;
2. the tables run back to back with identical sampling;
3. it records the environment, the Go version, the CPU, the git revision and **the list of
   uncommitted files**;
4. raw output goes to `results/latest/`, and one `BENCHMARK.md` is rendered.

Only numbers from the same `bench-report` run may be quoted side by side.

The report opens with a **Summary** that states the conclusions — which adapter wins, where
wrapping costs and where it saves, whether stdx beats the frameworks' own code. Every figure in
it is *computed from that run*: the win counts, the rankings and the middleware crossover
points are derived from the tables below them, so re-running cannot leave the prose asserting
something the numbers no longer support. Only the methodology caveats are fixed text, because
they describe the harness rather than the measurement. If you want to change what the summary
says, change `render_findings` in `report.py` — editing `BENCHMARK.md` is pointless, the next
run overwrites it.

Generated output goes exclusively under `results/latest/`, never into the same namespace as
the older data in `results/`. A generator sharing that namespace will eventually pick a name
an archived report already used and overwrite it — which is how the first round's
`environment.json` and `network.json` were lost.

**Nothing under `results/` is tracked.** `benchmarks/` has no `go.mod`, so it belongs to the
root module, and anything committed here ships in the module zip that every consumer of
`github.com/go-sphere/httpx` downloads — every adapter depends on the root module. Benchmark
samples have no business there. `BENCHMARK.md` carries the medians and the environment, and
the archived reports carry their own tables, so the conclusions survive without the raw output.
Re-run rather than reach for someone else's samples: benchstat across machines is meaningless
anyway.

## Running one table

```sh
make bench-adapter   # native vs httpx, 7 scenarios x 5 frameworks
make bench-suite     # the shared scenario table x 5 adapters, each on its own dispatcher
make bench-native    # the shared scenario table x hand-written implementations with no httpx
make bench-network   # fixed-rate Vegeta load; needs vegeta installed separately
```

Override the sampling with `BENCH_COUNT` (default 12) and `BENCH_TIME` (default 200ms). 12 is
the smallest count that kept every row within ±15% on the reference machine; 6 produced rows
above ±50%, which benchstat cannot tell from a real change.

Judge significance with benchstat, not by the decimal places in the rendered tables:

```sh
go install golang.org/x/perf/cmd/benchstat@latest
benchstat -row /framework,/scenario -col /mode results/latest/adapter.txt
benchstat -row /scenario -col /adapter results/latest/suite.txt
benchstat -filter '/mode:httpx' before.txt after.txt   # both sides must be the same benchmark source
```

Vegeta is used as a CLI only, so no load-testing dependency enters any `go.mod`:

```sh
go install github.com/tsenart/vegeta/v12@v12.13.0
python3 benchmarks/network.py --rate 5000 --duration 10s --repeat 5
```

The script looks for vegeta on `PATH` and in `~/go/bin`, and accepts `--vegeta /path/to/vegeta`.

## Layout

| Path | Contents |
| --- | --- |
| `BENCHMARK.md` | The current baseline. Generated — do not edit by hand. |
| `report.py` | The generator: every table in one run. |
| `network.py` | Fixed-rate network comparison, also invoked by `report.py`. |
| `results/` | Raw samples: `latest/` from the most recent run, the rest frozen from past experiments. **Not tracked.** |
| `bin/` | Compiled test binaries. Not tracked. |
| `history/` | Records of past optimization rounds; see [history/README.md](history/README.md). |

## Scenarios and measurement boundaries

Scenarios are defined once, in `httpxtest/scenarios.go`, and shared by the contract tests and
the benchmarks — adding a scenario adds both a contract and a benchmark. `BenchmarkOnly` marks
the ones whose response is too large to record as a golden.

The in-process tables drive each framework's own dispatcher: gin, echo and net/http through
`ServeHTTP` with a reused request and a writer that discards the body; fiber through its
fasthttp handler; hertz through `ServeHTTP` with a reused `RequestContext`. The necessary
context resets, hertz's URI setup and route resolution are all inside the timed section.
Per-request state is cleared between iterations — including the multipart form that net/http
memoizes on the request, without which only the first iteration would parse it while fiber and
hertz, whose runners reset their native request, parse every time. Responses are validated
before timing starts.

`StateParallel` reports the combined processing time across workers divided by iterations; it
is not a single-request latency.

**Not covered**: databases and RPC, HTTP/2, TLS, real network round trips, sustained throughput
on long-lived streaming responses, peak QPS under load from a separate machine. None of the
percentages in the report extrapolate to "endpoints got N% faster".
